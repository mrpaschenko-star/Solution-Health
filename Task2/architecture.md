# Целевая интеграционная архитектура

## Контекст и границы

[C4 Level 1 PNG](to-be.png) · [PlantUML](to-be.puml). Пациент — человек, а мобильное приложение показано как **внешняя программная система, исполняющая роль нового актера**. На L1 представлены системы и взаимодействия; API Gateway, брокер, БД и кеши описаны в ответственности систем, а не выданы за самостоятельных бизнес-акторов.

Фокус — новая «Мобильная платформа»: пациентский API, API Gateway/BFF и сохраняемый процесс записи с оплатой. Отдельные новые границы — IAM, доставка/чтение медицинских результатов и шлюз ДМС. Они изолируют legacy-контракты и имеют владельцев данных/восстановления. Реализация начинается с нескольких модулей и отдельных workers; не требуется разворачивать микросервис для каждого шага SAGA.

Существующие расписание (Java/REST/PostgreSQL), CRM (Java/REST/PostgreSQL), LIS (SOAP/FTP/REST), 1С (HTTP-шлюз), веб-портал, PSP и уведомления сохраняются. Расписание владеет слотами/записями, CRM — карточкой пациента, LIS — медицинским результатом и его версией. Новый read-store результатов — производная модель, не место редактирования медицинского заключения. Шлюз ДМС хранит проекцию и наблюдения проверок, 1С остаётся источником покрытия. Платёжный модуль владеет operation/payment ledger и сверкой, провайдер — фактическим движением денег.

## Новые и изменяемые интеграции

| ID / взаимодействие | Паттерн и протокол | Почему / гарантия |
|---|---|---|
| I01. Приложение ↔ IAM | OIDC/OAuth 2.0 Authorization Code + PKCE через системный браузер; HTTPS | Публичный native client без встроенного секрета; единая идентичность и отзываемые сессии |
| I02. Приложение → пациентский API | HTTPS REST/JSON, `/api/v1`, bearer access token | Совместимость с мобильными клиентами; Gateway проверяет auth/rate limits/размер, BFF собирает только разрешённый ответ. Новое приложение не обращается к legacy напрямую |
| I03. API → процесс записи → расписание | Быстрый durable accept `202` + polling операции; workers вызывают idempotent REST reserve/confirm/release | SAGA не живёт в HTTP-соединении; owner и шаги переживают рестарт. Внутри расписания atomic conditional updates и ограничение слота |
| I04. Процесс записи → платёжный модуль → PSP | REST create/payment redirect + подписанный callback; GET status/reconciliation | Idempotency/business key, amount/currency/booking correlation; timeout ведёт в unknown, а не в повторный новый платёж |
| I05. Процесс записи → шлюз ДМС → 1С | Anti-corruption adapter, bounded HTTP, cache/coalescing/async refresh | Защищает от JSON/XML drift и >50 RPS; null/timeout — unknown. Для платной записи без ДМС запрос не нужен |
| I06. Процесс записи → резерв лаборатории | Adapter к подтверждённым reserve/confirm/release с idempotency; транспорт SOAP/REST по реальному контракту | Во входных данных такого write API нет. Включать комбинированный сценарий только после проверки capability и владельца ресурса |
| I07. LIS → контур результатов | Incremental pull с checkpoint/reconciliation; push ускоряет при наличии durable contract; transactional outbox → RabbitMQ | Не требует немедленно переписать LIS; повторная выгрузка закрывает потери. Минимальный payload событий и независимые подписчики |
| I08. Контур результатов → CRM и read-store → API | Durable subscriptions, inbox + versioned upsert; приложение читает через API | Медленный CRM consumer не блокирует пациента. CRM migration через staging/shadow, затем единственный активный writer нового маршрута |
| I09. Бизнес-процессы → уведомления | Outbox → persistent RabbitMQ/quorum queues → consumer ACK после durable handoff | Уведомление не часть транзакции оплаты. Раздельные очереди transactional/marketing/results, приоритет записи; повтор не меняет бизнес-статус |
| I10. API/процесс → CRM | REST получения минимальной карточки + защищённое связывание subject с patient ID | Не принимать `patientId` из клиентского запроса как доказательство доступа; связь подтверждается отдельно, возможные однофамильцы не сливаются |
| I11. Веб-портал → общие команды/платёжный модуль | Поэтапное направление mutating flows через ту же идемпотентную границу | Иначе старый канал продолжит создавать дубли и обходить лимит 1С. Временный прямой доступ учитывается в общей квоте и инвариантах владельца данных |

## Сочетание архитектурных стилей

Сервисная интеграция оставляет ответственность существующим системам. API Gateway + BFF даёт единую внешнюю поверхность, но не содержит медицинских/финансовых правил. Для чтения используются REST и CQRS-проекции; события передаются асинхронно через уже имеющийся RabbitMQ, а оркестрируемая SAGA согласует длительную бизнес-операцию. Anti-corruption adapters нормализуют 1С/LIS, не заставляя native client понимать их XML/SOAP.

Предлагаемый Gateway — Envoy с проверкой JWT, централизованным rate-limit service и OpenTelemetry; аналог допускается по навыкам эксплуатации. Durable idempotency находится в командном модуле и сервисах-владельцах, а не в памяти Envoy. RabbitMQ выбран ради повторного использования стека; параметры кластера необходимо исправить и испытать. Внедрение Kafka без необходимости многопотребительского длинного replay увеличило бы эксплуатационную стоимость; журнал/outbox и зашифрованный архив результатов дают адресный replay.

API, оркестратор, consumers масштабируются горизонтально, но используют отдельные connection pools и bulkheads для legacy. На первом этапе можно разделить схемы/роли новых хранилищ в HA PostgreSQL с проверенным ресурсом; это не прямой доступ к таблицам расписания/CRM. Целевое разделение owners не означает обязательного числа физических кластеров.

## Открытые контракты и критерии запуска

| Пробел | Владелец / требуемое решение | Что блокирует |
|---|---|---|
| Резерв лабораторного ресурса не описан | LIS vendor + лаборатория: API, authority, expiry, idempotency, confirm/release; при отсутствии — отдельный согласованный booking registry, используемый всеми каналами | Комбинированная запись; нельзя имитировать реальный резерв строкой в БД SAGA |
| PSP: idempotency window, callback/status/refund/cancel | Финансы + провайдер: договор, статусная модель, merchant reference lookup, duplicates/unknown outcome | Повторы mutating вызовов, автоматические возвраты, live payment pilot |
| LIS change/export semantics | Лаборатория + интеграции: result ID/version, corrected/retracted/final states, watermark, возможность повторной выдачи и patient mapping | Гарантия полноты доставки и безопасное отображение результата |
| Правила ДМС | Страховой бизнес + 1С: service/clinic/date scope, stale decision, отзыв и смена coverage, формат ответа | Использование cached decision для финансовой авторизации; fail-open запрещён до отдельного согласования |
| Идентичность/доступ | ИБ + клиники: связывание subject/patient, представители/дети, врачебные права, согласия | Показ медицинских данных; MVP — только собственная подтверждённая карточка |
| Нагрузка/доступность/DR | Эксплуатация + продукт: session activity, peak mix, payloads, RPO/RTO, граница SLO и dependency budget | Подтверждение 50 000/p99/99.95 и выбор topology |
| Retention и размещение | ИБ/юристы: сроки медицинских данных, audit/financial retention, локализация, внешние push/PSP | Production-копирование/архив и провайдеры; число лет хранения не выдумывается |

## Приёмка перехода

До пилота обязательны: отсутствие дублирующей записи/списания в concurrent/retry тестах; recovery при потере ответа, callback и рестарте worker; восстановление outbox/inbox; объектная авторизация пациента; измерение API latency и завершения операций. Новые read-маршруты сначала сверяются на одной версии результата; legacy LIS→CRM writer отключается только после доказанной полноты нового маршрута, без двойного исполнения.

Пилот ограничивается согласованной клиникой/группой. При rollback прекращают приём новых операций новой версией, а уже начатые SAGA доводят/компенсируют их единственным владельцем. Возврат клиента на старый экран не разрешает повторную оплату неизвестной операции. Мониторинг и support console показывают operation ID, последний подтверждённый шаг и причину ожидания без медицинского payload в логах.
