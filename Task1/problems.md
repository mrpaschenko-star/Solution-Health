# Проблемы текущих интеграций

Таблица основана на [E01–E06](../sources/README.md). Проблемы сгруппированы по механизму, а не только по сервису. Обозначение приоритета — оценка проекта: P0 блокирует безопасный запуск, P1 требует решения до расширения; объём и частота инцидентов нуждаются в измерении.

| Проблема | Признаки | Влияние на приложение |
|---|---|---|
| P0. Неоднозначный исход оплаты и повторное списание | INT-001: деньги списаны при timeout, статус не зафиксирован; SD-009: двойное списание; SD-004: зависание тестового приложения; Марина, E04: акцию пришлось свернуть | Повтор кнопки/запроса может списать деньги ещё раз; приложение ошибочно сообщает об отказе, нужны сверка и возвраты |
| P0. Нет идемпотентности записи и защиты бизнес-инварианта слота | INT-005, SD-003; Дмитрий, E04 прямо подтверждает отсутствие защиты повторного POST | Две записи на один ресурс, конфликт при визите; защита только в Gateway не закрывает гонки других каналов |
| P0. Нет сохраняемого процесса записи с оплатой и лабораторией | SD-002: `Booking not found` для paymentID; E03/E06: оплата есть, подтверждение/слот потеряны; условие 3.2 описывает отсутствие отката | Частичный успех нескольких систем остаётся без владельца; деньги, приём и лаборатория расходятся |
| P0. Недоступность полиса трактуется как бизнес-решение | INT-003, SD-001, SD-008: 503, >30 с, null и затем успешная проверка; Алексей, E05: через 5 с без ответа полис считают временно валидным без согласования бизнеса | Ложный отказ пациенту либо необеспеченная услуга за счёт ДМС; ответ unknown нельзя превращать в valid/invalid |
| P0. SQL-инъекция и подозрение на нарушение изоляции пациента | INT-006: SQL-инъекция поиска; SD-007: врач видит чужого пациента, возможная подмена сессии | Утечка медицинских/персональных данных; исправления должны охватить старый портал, API и объектные права, а не только TLS нового клиента |
| P1. Ненадёжный приём с оборудования и доставка LIS → CRM | INT-002, SD-005; Елена/Алексей, E05: FTP ошибки, разрывы, нет автоматического восстановления, старый Perl-коннектор без сопровождения | Результат не появляется либо задерживается до двух часов; пациент звонит, врач опирается на неполные данные |
| P1. Нет устойчивого ключа результата и учёта версии | INT-008: дубли XML и анализов; INT-011: устаревшая CRM, сообщение застряло | Дубли/пропуск исправления, неверное представление медицинской истории. Нужны result ID, версия и идемпотентный upsert, а не сравнение только файла |
| P1. Общий RabbitMQ и неописанные ограничения | INT-004, SD-006; Елена, E05: большие очереди и уведомления на том же брокере; подтверждения теряются | Пик маркетинговых пушей влияет на запись/результаты; retry storm усугубляет перегрузку. Нужны изоляция, durable handoff, мониторинг возраста и DLQ |
| P1. Блокировки расписания и отсутствие разгрузки чтения | INT-009; Дмитрий, E04: таблица слотов блокируется; E06: врачи ведут Excel | Поиск/изменение медленные, приложение показывает устаревшие слоты; увеличение числа API-инстансов само по себе не снимает DB contention |
| P1. Синхронная зависимость интерфейса от медленных legacy | E02: портал синхронно вызывает 1С, расписание и PSP; SD-001/004: >30 с / 10 с | Один зависший upstream удерживает ресурсы и портит пользовательский сценарий; нужен ограниченный sync read-path и долговечные async commands |
| P1. Нестабильные контракты и отсутствующая документация | Алексей, E05: 1С меняет JSON на XML без предупреждения; LIS-коннектор не документирован; INT-010 требует нового API Gateway | Мобильный релиз ломается от внутренних изменений; нужна anti-corruption boundary, versioned schema и consumer contract tests |
| P1. Нет сквозной наблюдаемости | INT-007; SD-002: booking/payment correlation нарушена; ручные перезапуски в E05 | Нельзя быстро найти зависшую операцию, отличить timeout от фактического списания или измерить end-to-end freshness |
| P1. Нет безопасного пациентского канала выдачи результатов | Анна/Олег, E03: результаты доступны сотрудникам CRM, пациентам их отправляют по email/скриншотами | Мобильное приложение не достигнет цели самообслуживания; перенос скриншотов в push создаст дополнительную утечку |
| P1. Capacity/HA/DR не подтверждены | E01 задаёт 500/50 000 пользователей, p99 и availability, но не workload/RPS, event sizes, топологию, RPO/RTO; текущие инциденты показывают недостаток резерва | Нельзя доказать целевую нагрузку, выбрать число реплик и обещать восстановление. Нужны профиль трафика и испытания отказа/restore |

Приоритет MVP: P0, ограничение зависимостей, корреляция и надёжность уведомлений. Лабораторный pipeline проектируется с учётом обеих границ — оборудование → LIS и LIS → приложение: исправление только второй не создаст результат, который ещё не принят LIS.
