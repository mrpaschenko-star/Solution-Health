# Надёжная доставка лабораторных результатов

Выбран integration adapter с устойчивым журналом приёма, transactional outbox, RabbitMQ и независимыми consumers для CRM и пациентской модели чтения. Основной способ получения — повторяемая инкрементальная выгрузка подтверждённых LIS-результатов; push при наличии надёжного контракта ускоряет доставку, а сверка с LIS остаётся страховкой. Приложение получает результат через защищённый API, push сообщает только о готовности.

## Сравнение вариантов

| Вариант / инструмент | Доставка и исправления | Пиковая нагрузка / эксплуатация | Решение |
|---|---|---|---|
| Синхронный LIS → CRM → приложение, доработка текущего REST-коннектора | Timeout/падение CRM по-прежнему разрывают цепочку; нужен журнал повторов и reconciliation | Меньше новых компонентов, но зависимость доступности и общей задержки | Не выбран как единственный путь |
| Только polling CRM приложением | Не восстанавливает потерю LIS → CRM, не различает отсутствие результата и задержку | Каждый пациент усиливает read-нагрузку; кажется простым, но сохраняет дефект | Не решает источник проблемы |
| Webhook LIS → RabbitMQ без журнала/reconciliation | Надёжен только если LIS гарантирует повтор до durable ACK; это не подтверждено | Низкая задержка, но скрытая потеря при сбое отправителя | Дополнительный fast path после contract tests |
| Adapter + повторяемая выгрузка + outbox + RabbitMQ | At-least-once, durable acceptance, версии/inbox, сверка и replay; источник должен уметь повторную выдачу | Использует существующий брокер; consumers и pull batching регулируются независимо, есть нагрузка сверки | **Выбран**; клинические очереди изолированы от маркетинга |
| CDC БД LIS + Kafka | Хороший технический capture при доступных логах, но изменения строк не равны финальному медицинскому результату | Новая платформа и права/лицензии, vendor schema coupling; необоснованно для MVP | Рассмотреть позднее при доказанной пользе, не предполагать DB-доступ |

## Поток и границы гарантии

[Блок-схема PNG](lab-flow.png) · [PlantUML](lab-flow.puml).

1. Оборудование передаёт данные в LIS. Для существующего FTP добавляются устойчивый spool, контроль завершённости файла, checksum, журнал попыток и автоматическое повторное получение с источника. `.part` → atomic rename или completion marker используется только если стороны поддерживают этот протокол. Проверка размера/доступности порта не равна проверке медицинской полноты.
2. LIS валидирует и публикует финальный результат. Начало нашей end-to-end метрики — момент доступности разрешённой к выдаче версии в LIS, а не время запуска job. Лаборант по исходному кейсу имеет только чтение; ручной replay выполняет уполномоченная эксплуатационная роль, без изменения медицинского содержимого.
3. Adapter получает `resultId`, `version`, `status`, источник patient reference, specimen/order reference и время финализации. Требуется устойчивый incremental cursor с определённым порядком; при timestamp pagination нужны tie-breaker и перекрывающийся интервал. Отсутствие изменённых строк не доказывает отсутствие пропуска: периодическая reconciliation сравнивает набор IDs/versions за согласованное окно, включая исправления старых исследований.
4. В одной локальной транзакции сохраняются разрешённый payload/ссылка на него, source version, inbox/dedup record, outbox и checkpoint. Checkpoint продвигается только после durable commit всего принятого диапазона. Если JSON/XML нарушает контракт или patient mapping неоднозначен, запись помещается в защищённый quarantine с причиной; потерянный диапазон не объявляется обработанным.
5. Outbox relay публикует persistent сообщение в durable exchange с `mandatory` и publisher confirms. Сбой до/после confirm приводит к повтору; outbox не удаляется до подтверждения маршрутизации/доставки по принятой политике. Broker backpressure останавливает relay, журнал остаётся источником повторной доставки.
6. Два независимых consumer-потока: пациентский read-store и CRM adapter. Read-store атомарно пишет inbox и результат/версию, затем ACK. CRM adapter ACK после подтверждённого upsert; если CRM не поддерживает inbox/idempotency, нужен conditional upsert по внешнему result ID/version или чтение-сверка после unknown outcome. Собственный inbox адаптера **не обеспечивает** атомарность с удалённым CRM сам по себе.
7. После durable применения read-store публикует `ResultAvailable` через свой outbox. Notification worker отправляет нейтральный push «Доступен новый результат» без диагноза, типа анализа и ФИО. Пациент открывает приложение, проходит auth, API проверяет ownership и читает разрешённую актуальную версию. Недоставка push не скрывает результат в приложении.

Если оборудование не передало данные, adapter не может восстановить отсутствующий LIS-результат. Если LIS не предоставляет ни replayable API/export, ни надёжный push, заявлять гарантированную поставку нельзя: до production требуется доработка поставщика или поддерживаемый export agent. Гарантия проекта — сохранение принятых событий и eventual delivery при восстановлении зависимостей, достаточном retention и устранении quarantined данных; не мгновенная доставка при любой аварии.

## Идентичность, версии и медицинская корректность

Ключ результата: `(sourceSystem, resultId)`, ключ изменения: `(sourceSystem, resultId, version)`. File name/transport message ID и checksum недостаточны: один файл могут переименовать, а результат может быть законно исправлен. Разные версии сохраняются по policy, read-model выбирает последнюю подтверждённую версию, предыдущий поздний дубль её не затирает. Если две записи одной версии имеют разное содержимое, это конфликт для лаборатории, не правило «последняя победила».

Статусы `preliminary`, `final`, `corrected`, `retracted` согласуются с LIS. До согласования пациентам выдаются только разрешённые финальные версии; исправление заменяет доступную версию с отметкой, отзыв скрывает/помечает отозванный результат по клиническому правилу. Order ID, фамилия или телефон отдельно не дают права на результат: необходима подтверждённая связь LIS patient → CRM patient → IAM subject. Представители/дети требуют отдельного permission grant.

## RabbitMQ, повторы и эксплуатация

Предлагается RabbitMQ quorum queues с тремя узлами в независимых доменах отказа и majority-доступностью, publisher confirms и manual ACK. Клинический поток отделяется от marketing не только routing key, но и ресурсными лимитами; для целевого контура — отдельный broker cluster или выделенная доказанная ёмкость. Один vhost не обеспечивает изоляцию CPU/диска. Точные storage/retention считаются из events/sec, размера, допустимого простоя и RPO; не заменяются числом пациентов.

Обработка transient ошибок: первая попытка, затем повторы через **5, 30 и 120 секунд** с jitter до 20%; всего четыре попытки одной доставки, затем parking queue и alert. Нельзя делать бесконечный immediate requeue. Parking не означает удаление: сохраняются payload/reference и причина; после устранения — контролируемый replay с тем же business key. Надёжность DLQ перехода проверяется для выбранной версии quorum queues (at-least-once dead-lettering) либо применяется явный durable republish с confirm до ACK исходного сообщения.

Bounded queues используют reject-publish/backpressure, а не drop-head для клинических событий; outbox хранит непринятые публикации. Prefetch/число consumers настраиваются по времени обработки и лимитам CRM; добавление workers не обходит downstream quota. Broker queue не является медицинским архивом: защищённый source journal/read-store имеют собственные backup/retention/restore.

## Задержка и приёмка

Проектное начало: incremental pull раз в **15 секунд**, paging/batch ограничены согласованной квотой LIS; reconciliation — каждый час плюс ежедневная контрольная сверка доступного периода исправлений. При отсутствии vendor cursor выбор интервала перекрытия зависит от измеренного late-arrival/clock skew и не фиксируется по догадке. Предлагаемый ориентир после появления final в LIS: p95 ≤60 с, p99 ≤120 с в согласованном профиле нагрузки. Это новые цели для согласования, не SLA из документа.

Метрики: ready-in-LIS → visible-in-API latency, oldest unprocessed age, checkpoint progress, outbox/quarantine/parking size, IDs/versions discrepancies, ACK/confirm failures, свободный диск, duplicate/conflict rates. Пустая очередь не означает актуальность, если сломан pull; нужен source heartbeat и сверка. Внешняя недоступность видна в общей свежести, а не исключается из отчёта молча.

Испытания: повтор XML под другим именем; исправление после старой версии; потеря подтверждения publish/upsert; рестарт после DB commit до ACK; отключение CRM; переполнение брокера; частичный FTP-файл; неоднозначный patient mapping; отозванный результат; restore и replay. Успех — доступная разрешённая версия без логических дублей, исходный payload не потерян после durable acceptance, чужие данные не выдаются. Rollout нового LIS→CRM пути: shadow/staging сравнение, отключение legacy writer, включение одного нового владельца; при возврате сперва остановить новый writer и сверить позиции.
