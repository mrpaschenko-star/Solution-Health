# Контракт списка записей

[openapi.yaml](openapi.yaml) описывает `GET /api/v1/appointments?status=upcoming&limit=20&offset=0`. Спецификация OpenAPI **3.2.0** выбрана по конкретному пункту 3.3; итоговый список исходного документа противоречиво называет 3.0. Версия формата OpenAPI независима от версии внешнего API `v1` и `info.version: 1.0.0`. Инструменты, понимающие только 3.0, потребуют отдельного конвертированного представления; нельзя просто заменить число версии из-за nullable-схем JSON Schema.

## Ресурс и семантика

Результат содержит минимальные сведения записи: публичный ID, состояние, время/таймзону, врача и клинику; диагнозов, анализов, номера полиса и платежных реквизитов здесь нет. Сервер получает patient identity из подтверждённой связи OAuth subject, клиент не выбирает её параметром. Непрозрачность UUID не заменяет проверку ownership.

`status=upcoming` — фильтр: запись подтверждена, `startsAt >= generatedAt` страницы. Это не отдельное состояние записи. Временные holds и незавершённая SAGA доступны через operation endpoint и не появляются как подтверждённые appointments. `cancelled`/`completed` выбирают соответствующие конечные состояния. Время сравнивается в UTC, IANA timezone нужна для отображения в четырёх городах и при поездках пациента.

## Пагинация

Offset/limit выбраны по требованию задания и небольшому списку записей одного пациента; default limit **20**, maximum **100**, offset **0–10000** — проектные ограничения. Фильтрация по пациенту и статусу выполняется до pagination. Сортировка `(startsAt ASC, id ASC)` детерминирована; индекс начинается с patient ID, затем нужных полей фильтра/порядка.

Читаются `limit + 1` строк, чтобы вычислить наличие следующей страницы без полного `COUNT(*)`; возвращается не более limit. Если следующая страница существует и её offset не выходит за 10000, `hasMore=true`, `nextOffset=offset+len(items)`, иначе `false/null`. Ограничение глубины явно означает предел этого API, а не доказательство отсутствия более старых записей; для большого архива нужен отдельный query/export контракт.

Между запросами записи могут отмениться/добавиться, а время перейти через начало приёма: offset не даёт snapshot и может пропустить или повторить элемент. Мобильный клиент объединяет элементы по ID и при обновлении возвращается к первой странице. Для частых изменений/большого архива следующая версия перейдёт на cursor/keyset или snapshot-token; текущий `generatedAt` не обещает стабильного снимка всей выборки.

## Ответы и версия

Основные требуемые коды с примерами: **200** — список (в том числе пустой), **401** — отсутствующая/недействительная сессия с Bearer challenge, **500** — непредвиденная ошибка без внутренних деталей. Дополнительно описаны 400/403/429/503, чтобы не скрывать валидацию, права, rate limiting и недоступность. При отказе хранилища нельзя возвращать `200 items: []`: это ложно сообщит пациенту об отсутствии записи.

Ошибки имеют `application/problem+json` по RFC 9457 и traceId без PII. `Cache-Control: no-store` применяется ко всем персональным ответам, включая ошибки; контент пациента не кешируется общей CDN. Указанные `.example` endpoints фиктивны. OIDC Authorization Code + PKCE описан в [security.md](../Task4.3/security.md); `appointments:read` требуется вместе с действительной сессией и patient mapping.

В `/api/v1` сохраняются смысл фильтров, сортировка, типы и обязательные поля. Необязательное additive поле допускается, старые клиенты игнорируют неизвестные поля; новое enum-значение нельзя молча считать совместимым, если клиент исчерпывающе обрабатывает enum. Breaking changes получают `/api/v2` с периодом совместного обслуживания и проверкой использования старой версии.

## Проверка

Скрипт [validate.py](../tools/validate.py) проверяет OpenAPI, локальные ссылки и примеры ответов против схем, а также параметры pagination/ownership surface. Он не заменяет реализацию или runtime security tests. На реализации дополнительно нужны тесты сортировки, времени, границ limit/offset, изоляции субъектов, revoked sessions и отсутствия ложного пустого ответа при сбое БД.
