# Отказоустойчивость 1С и платёжного шлюза

Значения ниже — **предлагаемая начальная конфигурация**, которую необходимо проверить на стенде с реальными распределениями latency и согласовать с провайдерами. Внешние вызовы выполняют workers сохраняемой SAGA, а мобильный запрос получает durable `202` и читает статус; 2–3 секунды upstream timeout не помещаются в годовой API p99 <1 с синхронной цепочки.

## Параметры вызовов

Количество попыток включает первый запрос. Deadline включает соединение, TLS, отправку и чтение; отдельный connect timeout — **0.5 с** внутри общего бюджета. Отмена локального запроса не отменяет удалённую операцию.

| Система / операция | Timeout, секунды | Повторы и интервалы | Fallback и обоснование |
|---|---|---|---|
| 1С: проверка покрытия, read-only | **2 с** на попытку; **6 с** общий budget одной worker-задачи | Всего **2 попытки**. Между ними random **0.2–0.4 с**; только transport/timeout/502/503/504 при закрытом breaker и доступной квоте. 429/503 с Retry-After — отложенная задача, без ожидания сверх budget. Null/невалидная schema не ретраятся немедленно | `POLICY_PENDING`/unknown, UI сообщает «проверка недоступна». Для экрана полиса можно показать кеш с временем проверки, для финансового допуска stale/unknown не превращаются в valid. Ограничивает зависания >30 с и исключает несогласованный fail-open из E05 |
| PSP: create/capture/refund | **3 с** на попытку | **1 попытка**, **0 автоматических повторов mutating запроса** после timeout. Один и тот же платёж не создаётся заново по инициативе клиента. После доказанной сверкой необработанности допустима новая отправка того же ключа в рамках отдельного recovery-решения и контракта PSP | `PAYMENT_UNKNOWN` или `REFUND_PENDING`; сохранить merchant reference, показать ожидание, запустить query/reconciliation. Нельзя объявлять declined, делать новый charge либо refund ещё не подтверждённого списания |
| PSP: безопасный GET status | **2 с** на попытку | Всего **3 попытки**, паузы **1 с и 3 с**, jitter ±20%; budget задачи **12 с**. Повторы только transient; затем повторная durable сверка через **30 с**, с alert при неизвестности **5 минут** | Операция остаётся unknown, slots/expiry обрабатываются по SAGA. Финансы получают incident/task; очередь сверки не создаёт повторные charge/refund. Значения требуют согласования rate limits PSP |

Validation/business errors и окончательный отказ не ретраятся. Retry-After имеет приоритет: если не помещается в budget, задача планируется позже с сохранённым состоянием. Budget attempts сохраняется между рестартами worker, иначе перезапуск превращает bounded retry в бесконечный. На background reconciliation устанавливается отдельная provider quota; «5 минут» — порог эскалации, не доказательство отсутствия списания и не автоматическая отмена.

## Приоритет Circuit Breaker

**В первую очередь — 1С.** Есть конкретные признаки перегрузки >50 RPS, зависания >30 с и каскадного удержания ресурсов; breaker вместе с rate limit/bulkhead быстро отсекает заведомо неуспешные вызовы. Для PSP breaker также нужен, но главная защита денег — persistent idempotency и сверка неизвестного исхода: открытый breaker не отвечает на вопрос, списаны ли деньги.

Стартовый профиль для 1С: скользящее окно **20 завершённых вызовов**, минимум **10**, открытие при **≥50%** transport/timeout/5xx ошибок либо **5 последовательных** таких ошибок. Неверный полис не ошибка доступности; null/schema mismatch — отдельный alert/карантин контракта и запрет использовать ответ. В состоянии Open **30 секунд** новые проверки не идут в 1С, выдаётся pending/разрешённое cached display. Half-open допускает **один probe одновременно**; после **трёх последовательных** успешных проверок — Closed, при неуспехе — снова Open.

Breaker state и probe lease координируются на уровне шлюза, чтобы каждая его реплика не устраивала собственный шквал проб. При потере координатора не применяется «каждому инстансу полная квота»: refresh останавливается, authoritative проверки переходят в pending либо идут через заранее выделенный ограниченный бюджет. Bulkhead: **до 10 одновременных вызовов 1С** в сумме, bounded waiting queue с deadline; переполнение отклоняет/откладывает новые проверки. Rate limit и bulkhead работают даже при Closed.

Для PSP предлагается отдельный breaker на mutating и status traffic: окно 20/minimum 10/50%, Open 30 с, один безопасный status probe. Тестовый charge/refund не используется как probe. Отказ charge endpoint не должен блокировать работающий status endpoint и подписанные callbacks. Все попытки, включая retries и probes, расходуют соответствующую provider quota.

## Разгрузка 1С

[C4 Level 1 PNG](policy-context.png) · [PlantUML](policy-context.puml). Новая система «Шлюз ДМС» объединяет adapter контракта, проекцию полисов, single-flight одинаковых проверок, общий limiter и refresh workers. Redis — кеш/координация внутри границы системы, а не источник страхового обязательства.

1. Display-кеш использует ключ `(patient, policy, service, clinic, serviceDate, contractVersion)`, **TTL 300 с**; UI показывает `verifiedAt`. Для null/timeout/schema error кеш положительного или отрицательного решения не заполняется. Доказанно отрицательный display-ответ кешируется **30 с**, чтобы быстро исправить данные без долгого ложного отказа.
2. Во время записи по ДМС выполняется authoritative проверка. Использование кешированного покрытия для оплаты допускается только после отдельного согласования допустимой давности и отзыва с бизнесом/страховщиком; по умолчанию при недоступности — pending. Это снижает преимущественно многочисленные просмотры/повторы, а не обещает обслужить любой объём уникальных проверок без 1С.
3. Одновременные запросы одного ключа объединяются single-flight. События изменения полиса, если 1С поддерживает надёжный export, инвалидируют версию; до этого применяется bounded refresh/scheduled reconciliation. TTL сам по себе не гарантирует немедленное обнаружение отзыва.
4. Общая стартовая квота всех вызовов нового шлюза — **20 RPS**, burst **5**, concurrency 10. Пример распределения бюджета — **15 RPS** пользовательским проверкам и **5 RPS** refresh/reconciliation, без превышения общего потолка; retries включены. Это запас относительно наблюдаемой деградации >50 RPS, а не подтверждённая безопасная мощность.
5. Web-портал постепенно переводится на тот же шлюз. До этого измеряется его прямая нагрузка: 20 RPS новому каналу нельзя разрешать автоматически поверх уже перегруженной 1С. Общий лимит утверждается по сумме каналов. За ним следят queue age, timeout rate и latency, а не только средний RPS.

Если очередь уникальных authoritative проверок стабильно растёт, добавление шлюзовых реплик её не исправит. Нужен совместно согласованный bulk/export/replicated-policy contract, увеличение мощности 1С либо ограничение приёма ДМС-операций с честным pending. Нельзя ради годовых 50 000 пользователей разрешить stale покрытие без бизнес-правила.

## Испытания и сигналы

Проверить 1С 503/timeout/null/смену JSON→XML, concurrent replicas, открытие/закрытие breaker, потерю limiter, restart worker и Retry-After. Для PSP — потеря ответа после успешного списания, duplicate/late callback, неизвестный refund и восстановление status API. Метрики: downstream attempts/RPS/inflight, breaker transitions, queue age, unknown money count/age, duplicate effects, cache hit/freshness, время итогового разрешения операции. Значения пересматриваются после нагрузочного теста; конфигурация версионируется и доступна для rollback.
