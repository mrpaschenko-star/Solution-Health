# Горизонтальное масштабирование

Выбраны **расписание и CRM** как две критичные существующие системы: первая принимает конкурентные записи/изменения врачей, вторая хранит пациентскую идентичность и используется сотрудниками для результатов. API/worker реплики должны быть stateless, а инварианты оставаться в транзакционных владельцах. Пациентское чтение результатов выносится в отдельную проекцию, чтобы не превращать каждый экран приложения в запрос к CRM.

## План для двух систем

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
|---|---|---|---|
| Расписание | Несколько Java API/worker реплик за LB, без sticky sessions; HPA по concurrency/latency и backlog, прогретый минимум под известные вечерние пики. PostgreSQL read replicas для поиска, кеш каталога врачей и доступности с меткой свежести. Reserve/confirm/release идут к writer; connection pool ограничен общим DB budget | **Горячий slot/write contention:** увеличение числа API или read replicas не ускоряет конкурирующее бронирование одного слота и может увеличить locks | Атомарный reserve с условием capacity/version, unique constraint активного единичного слота, idempotency в той же транзакции. Короткие транзакции без внешних вызовов; lock/deadline и admission control. По росту — владение/шардирование по clinic ID с явным routing и отдельной координацией ресурсов, общих для клиник; горячий слот всё равно сериализуется |
| CRM | Реплики REST API и consumer workers за LB; события пациентов/результатов разделены на очереди и key-based partitions; read replicas для допустимых внутренних чтений. Пациентский results read-store с отдельным API масштабируется независимо. Для крупного объёма CRM — partition/shard по устойчивому patient ID после измерений | **Lag и порядок обновлений одного пациента/результата:** больше consumers даёт out-of-order/дубли и более старое значение на replica | Inbox + conditional upsert по result ID/version, сериализация/optimistic version для конфликтующих patient updates. Patient merge имеет отдельную управляемую процедуру; replica только для допустимой давности. После записи read-your-write через writer/commit-watermark; неизвестность lag не маскируется. Проверки доступа используют authoritative связь subject/patient |

Шардирование не обязательно для MVP 500 пользователей: сначала устранить ошибки, измерить запросы/locks и разнести read/write. Репликация чтения не равна HA writer и не гарантирует отсутствие потери при failover. Для PostgreSQL нужны fenced failover, backup/PITR и restore drill; RPO/RTO и компромисс синхронной репликации утверждаются владельцем медицинских/денежных данных.

## Перевод пользователей в нагрузку

Во входных данных нет think time, доли активных сессий, request mix и размеров сообщений. Пример **сценария испытаний, не факта**: если все 50 000 активных пользователей отправляют в среднем один запрос раз в 10 секунд, получится 5 000 внешних RPS; при 500 — 50 RPS. Множитель burst 2 даёт тестовую точку 10 000 RPS для первого сценария. Смена частоты, background polling или доли активных пользователей меняет результат; 50 000 пользователей нельзя объявлять 50 000 RPS.

Для каждого класса запросов измеряются доля, fan-out, cache hit и read/write mix. Если lambda — нагрузка на конкретный сервис, а mu — проверенная производительность одной реплики **при целевом p99**, базовое число реплик выбирается из `N >= ceil(lambda / mu)` с запасом, достаточным при потере согласованного домена отказа. Значения mu/N нельзя вычислить из кейса. Число DB connections, consumers и запросов к 1С/PSP ограничивается отдельно: HPA не имеет права пропорционально увеличивать давление на legacy.

## Latency и доступность

Годовая цель: **p99 <1 с**, **99.95%**. Предлагаемый бюджет ответа пациентского API — 800 мс на обработку с резервом 200 мс на сеть клиента в согласованном регионе; границу end-to-end необходимо измерять на мобильных сетях. При недоступности зависимости API быстро возвращает честный pending/error, но это не засчитывается как успешное бизнес-завершение. Отдельно измеряются время полного бронирования, неизвестные платежи и свежесть анализов; целевые значения утверждает продукт вместе с клиниками.

99.95% соответствует **21.6 минуты** недоступности за 30 дней. Несколько последовательных зависимостей с доступностью 99.95% каждая не дают такой же доступности композиции; надо распределить error budget, исключить необязательные sync-зависимости и испытать весь путь. Реплики API/consumers распределяются по независимым failure domains; IAM, LB/Gateway, PostgreSQL, Redis и RabbitMQ не должны оставаться одиночными точками отказа. Для цели «масштабирование всех компонентов» 1С/LIS требуют vendor-поддерживаемой topology: адаптеры и кеш не делают их внутренние writers горизонтальными автоматически.

## Проверки от MVP к году

1. MVP: модель 500 одновременных пользователей с реальным read/write mix, вечерним burst, мобильными retries и конкуренцией за популярного врача. Проверить бизнес-инварианты и safety всех компенсаций.
2. Далее: ступенчатый рост активных сессий и нагрузка 50 000 по нескольким think-time сценариям, cold cache, массовое появление анализов, рекламный push и независимая CRM нагрузка врачей. Проверять p99 по endpoint, а не только общий средний процентиль.
3. На каждой ступени: потеря API replica, узла/домена брокера и DB failover; задержка 1С/PSP; очередь backlog + catch-up. HPA/staging тест не заменяет профиль p99 при отказе.
4. Gate расширения: нагрузка и доступность выдержаны, нет oversell/повторных списаний, lag/results соответствуют принятым SLO, fallback не перегружает legacy. Сохраняются отчёт нагрузки, runtime/config versions, restore evidence и решение владельцев.

Цели кол-центра/онлайн-записи измеряются отдельно: обращения по записи на сопоставимое число визитов и каналов, доля онлайн **состоявшихся визитов** среди всех визитов, baseline до запуска и сезонность. Уменьшение звонков из-за недоступности телефона не считается успехом. Рост среднего чека оценивается без навязывания медицински необоснованных услуг и с согласованными правилами рекомендаций.
